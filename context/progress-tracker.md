- Project name validation in the create dialog (follow-up request): special characters were silently dropped from the slug with no feedback. `lib/slug.ts` gained `hasUnsupportedCharacters()` and the `SUPPORTED_NAME_MESSAGE` constant alongside `slugifyProjectName()`. The check mirrors the slug pipeline rather than hardcoding a second rule — a character is supported when its normalized, diacritic-stripped, lowercased form is a letter, digit, space, or hyphen — so an accented `Cafe Ordering` passes (it maps to `cafe-ordering`) while `!`, `%`, `_`, em dashes, and non-Latin scripts do not. `useProjectActions` exposes `hasNameWarning` and `nameError`: typing raises a live warning, `submitCreate` refuses to close and sets the error while the name is invalid, and any edit clears the error. `CreateProjectDialog` renders one message row — the submit error (`text-error`, `role="alert"`, `CircleAlert`) outranks the typing warning (`text-warning`, `TriangleAlert`), both share an id wired through `aria-describedby`, and `aria-invalid` is set only after a submit is rejected so the primitive's destructive ring appears. Both messages state the allowed set rather than the offending characters — `Use letters, numbers, spaces, and hyphens.` — which is why the validator returns a boolean and no character list is formatted for display. Combining marks are judged by what they attach to rather than by their own form: they normalize away to nothing, so `hasUnsupportedCharacters` tracks whether the previous character was a surviving base letter. `Cafe` + `\u0301` (the decomposed spelling of an accent) is accepted just as the precomposed `Café` is, and a letter may stack several marks, but a mark with no base letter in front of it — `\u0301Project`, a mark after a space, hyphen, or digit — is rejected, because the slug drops it silently and the stored name would stop matching what was typed. A second rule rejects an empty slug: a blank, whitespace-only, or hyphen-only name passes the character check (space and hyphen are supported) but slugifies to nothing, and `submitCreate` was closing the dialog as if creation had succeeded with no derivable room ID. Those names now raise `NAME_NEEDS_SLUG_MESSAGE` — `Use at least one letter or number.` — with the character message taking priority when both rules fail. Only create validates: rename edits the display name and never regenerates the room ID. ## Architecture Decisions

- Editor chrome components live in `components/editor/` and are presentational shells: they take state (`isSidebarOpen`, `isOpen`, `open`) and callbacks from their parent and hold no state of their own, so later chapters can own project/dialog state without rewriting them.
- The project sidebar is an overlay (`fixed`, `z-40`), never a layout column — opening it must not resize or push the canvas.
- Editor dialogs are composed through `EditorDialog` rather than by using `components/ui/dialog` directly, so the modal styling (`rounded-3xl`, elevated surface, token colors) stays defined in one place.
- Theme is dark-only: `app/globals.css` defines the Ghost AI palette once in `:root` (no `.dark` class, no light variant) and maps it onto shadcn's semantic tokens plus the custom utility names in `context/ui-context.md`. New components must consume those tokens (`bg-base`, `text-copy-*`, `border-surface-border`, `text-brand`, etc.) — no raw Tailwind color classes or hardcoded hex values.
- `components/ui/*` are shadcn-generated and should not be hand-edited; extend/wrap them elsewhere if custom behavior is needed. This cuts both ways: theme tokens must not break the core Tailwind utilities those files rely on, which is why no theme color may be named after one (see `bg-base` in `app/globals.css` and the note in `context/ui-context.md`).
- Route protection lives in `proxy.ts` (Next 16 renamed `middleware.ts` → `proxy.ts`; only one such file is allowed per project). It is deny-by-default: anything not matching the sign-in/sign-up env vars goes through `auth.protect()`.
- Public routes are derived from `NEXT_PUBLIC_CLERK_SIGN_IN_URL` / `NEXT_PUBLIC_CLERK_SIGN_UP_URL` rather than hardcoded strings, so the public surface and the pages Clerk redirects to cannot drift apart. `createRouteMatcher` is deliberately unused — it is deprecated in `@clerk/nextjs` v7.
- Clerk appearance is configured once on `ClerkProvider` via `lib/clerk-appearance.ts`. New Clerk components inherit it; do not pass per-component `appearance` overrides unless a component genuinely needs to differ.
- Clerk's own user menu, profile, and sign-out flows are used as shipped — `UserButton` is rendered with no element-level customization.
- Project dialog state lives in one hook (`hooks/use-project-actions.ts`), not in the dialog components. The dialogs are controlled and stateless: fetches, navigation, and refreshes live in the hook (since `07`), and each dialog only renders the `error`/`isSubmitting` it is handed. It is named `useProjectActions` — the name `07` specifies — and `08`'s workspace sidebar should reuse it as-is; the delete redirect already keys off `useParams().roomId`.
- Only the create flow validates the project name, because it is the only one that derives a slug from it. The rule and its user-facing sentence both live next to `slugifyProjectName` in `lib/slug.ts`, so the validator, the slug, and the message can never disagree about what a name may contain. Validation copy states what is allowed rather than listing what was rejected.
- The create and rename dialogs wrap their input in a `<form>` and put the submit button in the dialog footer, associated back to the form with the `form` attribute. That is what makes Enter submit, since `EditorDialog` renders the footer outside the body.
- Slug generation lives in `lib/slug.ts`, apart from both the hook and the dialogs. `04` uses it only for the preview; `07` composes its unique room-ID suffix on top of the same function so the previewed slug and the stored room ID cannot diverge.
- Sidebar item actions are derived from the callbacks passed in, not from a role flag: `ProjectSidebar` hands `onRename`/`onDelete` to the owned list only, so a shared project structurally cannot render them.
- Database access goes through the single `prisma` export in `lib/prisma.ts`; nothing else constructs a `PrismaClient`. Import the generated types from `@/app/generated/prisma/client` (the `prisma-client` generator output), not from `@prisma/client`.
- Prisma models live in `prisma/models/*.prisma`, one file per domain; `prisma/schema.prisma` holds only the generator and datasource.
- `/api/*` is protected in `proxy.ts` without `auth.protect()`: Clerk's `protect()` answers a signed-out non-page request with a `404`, so the proxy checks `auth()` itself and returns `401 { error }`. Route handlers still call `getCurrentUserId()` and return `401` on their own — the proxy is a first gate, not the only one. Page routes keep `auth.protect()`.
- API responses: success bodies wrap the resource (`{ project }`, `{ projects }`); every failure is `{ error: string }` built by `lib/api-response.ts`. Project mutations are owner-only (collaborators get `403`), checked with `checkProjectOwnership` and repeated in the Prisma `where` so the write can never touch another user's row.
- All `prisma`, `@prisma/client`, and `@prisma/adapter-pg` packages must stay on the same version (currently `6.19.3`, classic engine). Upgrading any one alone breaks the adapter contract; move to Prisma 7 as a deliberate, all-packages change.
- The project ID is the room ID. The client builds it (`buildRoomId` in `lib/room-id.ts`: slug + random suffix) and sends it as `id` on create, and the API validates it with the same module's `isValidRoomId`. That way the create dialog's preview, the stored primary key, the `/editor/[roomId]` URL, and the Liveblocks room can never diverge, and no second unique column needs keeping in sync. The schema's `@default(cuid())` remains the fallback for callers that omit `id`.
- Server reads for project lists live in `lib/project-data.ts`, shared by server components and route handlers. Browser-side mutations go through `lib/project-requests.ts`, the only client module that calls the project API. Hooks orchestrate state and navigation but never call `fetch` directly.
- Mutation outcomes reach the editor home through `router.refresh()` re-running `app/editor/page.tsx`, not through optimistic client state. The server-fetched lists stay the single source of truth.
- Workspace access is decided on the server, in `getProjectAccess` (`lib/project-access.ts`), before any workspace UI renders: owner or collaborator, matched by the same case-insensitive email rule as `listSharedProjects`, so the sidebar never lists a project its user cannot open. Missing and unauthorized projects are deliberately indistinguishable (`null` → `AccessDenied`). Read access (owner or collaborator) is separate from mutation access (`checkProjectOwnership`, owner only).
- `EditorNavbar` stays one component for both editor screens; workspace-only content (project name, Share, AI toggle) is gated on its optional `workspace` prop rather than duplicated in a second navbar.
- The create/rename/delete dialogs are rendered through `ProjectDialogs` by every screen that mounts `ProjectSidebar`; each screen owns its own `useProjectActions()` instance and passes it in.
- The AI sidebar placeholder lives inline in `EditorWorkspace` and mirrors `ProjectSidebar`'s overlay mechanics on the right. `20-ai-sidebar-shell.md` extracts it into its own component.
- Collaborator API: listing is membership-gated (`getProjectAccess`, owner or collaborator); invite and remove are owner-gated (`ownerOnlyError` in `lib/project-guards.ts`) and owner-scoped again in the Prisma write. Route handlers needing the owner-only guard import it from `lib/project-guards.ts` rather than redefining it.
- Collaborator profiles (name, avatar) come from the Clerk Backend API at request time (`lib/clerk-profiles.ts`), never from a local user table. Profiles are best-effort: a Clerk outage degrades rows to email-only instead of failing the request.
- Browser calls to the app's API go through `lib/api-client.ts` (`sendApiRequest`). Per-resource request modules (`project-requests.ts`, `collaborator-requests.ts`) build URLs and validate response bodies on top of it, and hooks never call `fetch` directly.
- The collaborator list is fetched when the share dialog opens, and invite/remove results are applied from the API's response, not through `router.refresh()`. Nothing server-rendered on the page shows collaborators, so a refresh would do no work.
- Clerk avatars render through `next/image`. `https://img.clerk.com/**` is the only allowed remote image pattern in `next.config.ts`.
